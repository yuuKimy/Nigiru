# わさびパニック — ゲーム性検証（擬似ユーザーテスト）計画

ルールの正は [`wasabi-panic-chef-plan.md`](./wasabi-panic-chef-plan.md) §2・§8。  
バグ・表示の正は [`wasabi-panic-test-plan.md`](./wasabi-panic-test-plan.md) と [`wasabi-panic-ui-qa-plan.md`](./wasabi-panic-ui-qa-plan.md)。

本計画は **面白さ・テンポ・パニック感・難易度カーブ** を検証する。  
試験中は **依頼されていないプレイ数値を変えない**。数値調整は記録を見てから別タスクにする。

実施は **`npm run preview`（本番相当）** を優先する。

---

## 1. 目的

「わさびパニック」が **短時間カジュアルゲームとして成立しているか** を、開発者＋数名のプレイ観察で確認する。

重点する問い:

| # | 問い | 現行設計の仮説 |
| --- | --- | --- |
| T | **テンポ良く遊べるか？** | 1タップ即出荷・160ms クールダウン・素通り無ペナで、迷いより手早さが主役になる |
| P | **パニック感を体験できるか？** | 満席＋複数ゲージ同時減少＋繁忙波で「間に合わない」が起きる |
| D | **時間経過で難しくなるか？** | 入店間隔短縮（5s→2.4s / 90s）、席増加、繁忙、コンボ連動で我慢短縮 |
| V | **ネタのバリエーションは増やすとより楽しいか？** | 現行はマグロ固定・差分はわさび量のみ（読みやすさ優先）。増やす場合の得失を記録する |

---

## 2. 擬似ユーザーテストとは（本プロジェクトでのやり方）

本番のユーザビリティラボではなく、**短いプレイセッション＋観察シート** で代用する。

- **プレイヤー**: 2〜4 名（開発者を含めてもよいが、開発者だけでは 1 セッション以上、外の人を 1 名以上入れる）
- **観察者**: 1 名（操作はせず、発言・表情・つまずきをメモ）
- **説明**: シナリオごとに「説明なし／最小限」を分ける（§4）
- **記録**: 各ラウンド後に 5 段階＋自由記述。録画は任意（画面録画で可）

合格の軸は「**3 分続けて退屈しない／忙しくなったとき焦る**」。数値の正確さや UI の AA 準拠は別計画。

---

## 3. 現行プレイの前提（観察時に頭に置く）

検証時点の実装目安（コード上。試験中は変えない）:

| 項目 | 値・挙動 |
| --- | --- |
| 席 | 最大 4。開始 1 席 |
| わさび | なし / 普通 / 大盛り の 3 種のみ |
| 握りネタ | マグロ 1 種固定（見た目・判定ともわさび量だけ） |
| 出荷 | タップ即レーン左端。クールダウン 160ms。レーン上限 8 皿 |
| 難易度 | 入店 5000ms 始まり、90 秒かけて 2400ms まで短縮。繁忙は開始約 20 秒後、以降 32 秒周期で 12 秒 |
| 我慢 | 基準 14 秒。コンボ・繁忙で短くなる（下限 7.2 秒） |
| 終了 | 不満退席 3 回（クレーム 0） |

## 4. セッション構成

### 4.1 準備（全員共通）

- [x] `npm run build` が通る状態で `npm run preview` を起動（2026-08-22 実施）
- [ ] 横向きスマホ、または PC ブラウザ（Chrome 推奨）— PC Chrome のみ
- [x] 観察シート（§6）— `docs/fun-test-log/` に記録
- [x] タイマー（3 分・5 分用）— 数値シミュレーションで代替

### 4.2 ラウンド A — 初見（説明なし）

**目的**: ルール理解と「説明なしで短時間遊べる」体験の核（chef-plan §1）を見る。

1. タイトル画面を見せるだけ。「スタートして」とだけ伝える
2. **3 分** 自由プレイ（ゲームオーバーになればその時点で終了）
3. 終了後、プレイヤーに口頭で聞く（観察者がメモ）:
   - 何をすればよいゲームだと思ったか
   - いつ一番忙しかったか
   - また 1 回やりたいか（はい／いいえ／わからない）

### 4.3 ラウンド B — 理解後（最小説明あり）

**目的**: ルールを知ったうえでのテンポ・パニック・難易度カーブを見る。

1. 30 秒だけ説明:「下の 3 ボタンでわさび量を選び、客の注文どおりに流す。間違いは素通り。客のゲージが切れると減点」
2. **2 回連続** プレイ（1 回目 3 分 or ゲームオーバー、2 回目は必ず最初から）
3. 2 回目は **到達時間・スコア** を記録（上達感・難易度感の参考）

### 4.4 ラウンド C — 焦点観察（任意・開発者向け）

**目的**: 繁忙波・満席・レーン詰まりなど、設計意図の区間を意識的に触る。

観察者が時計を見ながらメモ:

| 目安時刻 | 見ること |
| --- | --- |
| 0〜30 秒 | テンポは遅すぎないか。最初の 1 客で退屈しないか |
| 20 秒前後 | 「繁忙!」表示。入店・ゲージが急に厳しくなるか |
| 60 秒前後 | 席 3〜4。複数ゲージ＋レーン上の皿。パニックのピークか |
| 90 秒以降 | 入店間隔が底に近い。以前より忙しいと感じるか |

1 回 **5 分** またはゲームオーバーまで。

### 4.5 ラウンド D — ネタバリエーション（仮説のみ・実装不要）

**目的**: 「ネタを増やすと楽しいか」を、現行版プレイ後の **想像・比較** で記録する（コード変更なし）。

プレイヤーに次を聞く:

- 今の「マグロ固定」で、わさび 3 種だけの判断は足りたか／足りなかったか
- もし席ごとにネタ（マグロ・エビ・いくら等）が違うと、楽しい／混乱する／どちらでもない
- ネタを増やすなら、**わさび量と同列** か **飾り程度** か

将来 A/B する場合は、別計画で「ネタ 1 種 vs 2 種（見た目のみ・判定はわさびのまま）」など最小差分に留める。

## 5. 評価軸と判定基準

各軸を **1（弱い）〜 5（強い）** で評価。3 未満が続く軸は改善候補とする。

### T — テンポ

| 点 | 基準 |
| --- | --- |
| 5 | 3 ボタン連打が気持ちよく、待ち時間がストレスにならない |
| 3 | たまにレーン待ち・クールダウンを意識するが、全体としてテンポは保たれる |
| 1 | 出荷がもっさり、1 タップの即応性が足りない／退屈が長い |

観察チェック:

- [ ] 正解時に「サクッ」と流れて満足退席まで一連で気持ちいい
- [ ] 素通り後すぐ次の出荷に移れる（罪悪感よりリズム）
- [ ] レーン 8 皿付近で操作が止まる「詰まり」が頻発しない

### P — パニック感

| 点 | 基準 |
| --- | --- |
| 5 | 満席時に「どれから！」と頭が忙しくなる。繁忙は明確に区切れる |
| 3 | 忙しいが、余裕で処理できる時間もある |
| 1 | 忙しくならない／忙しさが単調（ゲージだけが減る等） |

観察チェック:

- [ ] 4 席＋複数注文の不一致皿が重なると判断が追いつかなくなる
- [ ] 我慢ゲージの色変化（緑→黄→赤）が焦りのトリガーになる
- [ ] 「繁忙!」の前後で体感難易度に差がある
- [ ] パニックが **理不尽**（見えない・読めない）ではなく **操作量** に起因する

### D — 難易度カーブ

| 点 | 基準 |
| --- | --- |
| 5 | 2 回目プレイで「前より早く忙しくなった」と言える。90 秒以降が 30 秒より明らかに厳しい |
| 3 | 少しずつ忙しくなるが、ピークが弱い |
| 1 | 最初から最後まで同じ忙しさ／途中で急すぎて理解前に終わる |

観察チェック:

- [ ] 1 席→満席への段階がある（いきなり 4 客ではない）
- [ ] 2 回目の生存時間 or スコアが 1 回目より伸びうる（学習と難易度のバランス）
- [ ] ゲームオーバー原因が「操作ミス」と「詰まりすぎ」のどちら寄りか記録

### V — ネタバリエーション（仮説・口頭）

コード上は 1 ネタ。記録のみ。

| 記録 | 内容 |
| --- | --- |
| 現行で十分 | わさび 3 種だけで判断が楽しい／飽きない |
| 増やしたい | 見た目の変化が欲しい。ただし注文が読めなくなる懸念あり |
| 増やしたくない | 情報過多。今のままがよい |

## 7. 実施順と人数

最小:

1. 開発者 1 名がラウンド C を 1 回（設計意図の区間メモ）
2. 外の人 1 名がラウンド A → B（計 3 プレイ）

- スマホ実機 1 名追加（テンポ・タップ感）

## 8. 集計と次のアクション

### 8.1 集計

- 各軸の **中央値** と **最低値** を出す
- 3 未満の軸が 2 名以上 → **要改善**
- 自由記述から **重複する不満** を 3 つ以内に要約

### 8.2 改善の切り口（記録後に検討。試験中は触らない）

| 症状 | 検討方向（例） |
| --- | --- |
| T が低い | 出荷クールダウン、レーン速度、開始時の客数 |
| P が低い | 繁忙の長さ・周期、満席時のゲージ速度、SE の強調 |
| D が低い | 入店カーブ（90 秒）、我慢下限、2 回目との差 |
| V で「増やしたい」が多数 | 見た目のみ 2 ネタ、または席ごとランダム（判定はわさびのまま）のプロトタイプ計画 |
| V で「今のまま」が多数 | chef-plan §9 どおりネタ多種類化はスコープ外維持 |

数値変更は **本計画の記録を添えて** 別 PR・別会話で行う。

### 8.3 リリース判断との関係

- 機能 P0（test-plan）が通っていること
- 本計画で T・P・D が **いずれも中央値 3 以上**、または改善予定が明文化されていること

を「体験として出せる」目安とする。V は必須合格軸にしない（仮説）。

## 9. やらないこと

- 1 名・1 回だけのプレイで「面白い／つまらない」と断定
- UI 色・フォントの好み議論（ui-qa-plan に委ねる）
